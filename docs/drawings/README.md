# Drawings

The drawings in the docs are generated by four scripts. Three use only the Python standard library; `make_outline_svg.py` needs `cadquery` (see below).

| Script | Makes | From |
|--------|-------|------|
| [`make_panel_svg.py`](make_panel_svg.py) | `panel.svg`, used in the manual, and `panel-plain.svg`, the panel without captions, used on packaging labels | The faceplate KiCad file |
| [`make_assembly_svgs.py`](make_assembly_svgs.py) | `assembly-*.svg`, used in the assembly guide | The main PCB KiCad file |
| [`make_patch_svgs.py`](make_patch_svgs.py) | `patch-*.svg`, the patch examples in the manual | The faceplate KiCad file |
| [`make_outline_svg.py`](make_outline_svg.py) | `outline-front.svg`, `outline-side.svg`, `outline-iso.svg` — used in the README, manual and assembly guide in place of photos | The `.step` assembly in `hardware/` |

## Panel drawing

The panel drawing in the [user manual](../manual.md) ([`../images/panel.svg`](../images/panel.svg)) is generated from the KiCad faceplate file, [`MultipleFaceplate.kicad_pcb`](../../hardware/panel/MultipleFaceplate.kicad_pcb).

After changing the faceplate in KiCad, run this from anywhere in the repo:

```sh
python3 docs/drawings/make_panel_svg.py
```

### What it reads

| From the KiCad file | Used for |
|---------------------|----------|
| `Edge.Cuts` lines | Panel outline |
| Mounting-hole footprints and their drill sizes | Jacks (Ø6.0), the link button (Ø6.5) and the rack screw holes |
| `F.SilkS` lines, circles and text | Printed lines, the switch symbol and the labels |
| The `SchentronicsLogo` footprint | The logo, read as its silkscreen polygons and placed at the footprint's position and rotation |

The script tells holes apart by drill size, so if you change a hole size, update `JACK` and `SWITCH` at the top of the script. The "Bank A", "Bank B" and "Link button" labels are added by the script, not read from KiCad.

The faceplate file is KiCad 10's S-expression format, read with a small generic S-expression parser in the script (not regexes), since the logo's artwork lives inside a footprint and needs that footprint's position and rotation applied to come out right.

## Assembly drawings

After changing the main PCB in KiCad, run:

```sh
python3 docs/drawings/make_assembly_svgs.py
```

| Drawing | How it's made |
|---------|---------------|
| `assembly-1-switch.svg` | Front and back board views, drawn from the board outline, pads and front silkscreen in the PCB file |
| `assembly-2-cap.svg` | Hand-built side diagram, not from KiCad |
| `assembly-3-faceplate.svg` | Side diagram. The part positions along the board come from the PCB file, and the heights are approximate. |
| `assembly-4-jacks.svg` | Back board view, drawn from the PCB file |

The side views assume the faceplate sits 27 mm further along than the PCB, matching the two KiCad files. If you move the jacks on either board, update `offset` in `fig_faceplate`.

## Patch examples

The patch drawings reuse the panel drawing and add module boxes and cables. Each example is a short function in the script, for example:

```python
def pitch(data):
    p = Patch(data)
    p.source("A1", "Sequencer", "pitch CV out")
    p.dest("A2", "VCO 1", "V/oct in")
    ...
```

Jacks are named by bank and position from the top: `A1`–`A4` and `B1`–`B4`. Sources go on the left, destinations on the right. Pass `color=BLUE` to draw a second signal. To add an example, write a new function, add it to the list in `main()`, and run:

```sh
python3 docs/drawings/make_patch_svgs.py
```

## Outline drawings

`outline-front.svg`, `outline-side.svg`, one `outline-iso-{top,bottom}-{left,right}.svg` per corner, and `outline-bare-parts.svg` are real projections straight from [`ST01_Multiple.step`](../../hardware/ST01_Multiple.step) in `hardware/` — not diagrams. They replace the old product photos in the README, manual and assembly guide. All four isometric corners are generated every run so there's always a fresh set to pick a hero shot from; `outline-iso-top-left.svg` is the one currently used. `outline-bare-parts.svg` is different from the rest: instead of the fully assembled module, it shows the panel and the bare (unpopulated) PCB board side by side — what a builder actually has in hand before assembly — built from `bare_parts_paths()` in the script, which keeps each part's real relative Y position from the assembly (only shifting the board sideways in X) so their jack positions line up vertically, same as they will once assembled.

This needs [`cadquery`](https://cadquery.readthedocs.io/) (`pip install cadquery`; no FreeCAD or other CAD tooling needed) for its hidden-line-removal (HLR) algorithm, which works out which edges of the real 3D geometry are visible from a given direction:

```sh
pip install cadquery
python3 docs/drawings/make_outline_svg.py
```

(or name one view to regenerate just that one, e.g. `... outline-front.svg`)

**This is slow, and not predictably so.** HLR is real geometric computation, not a quick export. Looking straight down an axis where many cylindrical parts line up end-on — our front view, with all 8 jacks' barrels coaxial with the view — is a worst case for the algorithm: the orthographic version of this view took **24 minutes**, against about a **minute each** for the side and isometric views of the same assembly. Time a new view on a copy before assuming it'll be quick.

**The front view also needed more than patience — read the module docstring in `make_outline_svg.py` before touching it.** Looking straight down all 8 jacks' coaxial barrels doesn't just make exact-BRep HLR slow, it makes its visibility tie-breaking unreliable: a different jack would come out missing its inner circle, doubling a ring line, or missing its outer ring, depending on what was tried — never a real difference in the geometry (confirmed by isolating any single jack + the panel, which always rendered correctly). Nudging the orthographic projection direction off-axis by a small tilt does **not** reliably fix this — a tilt that fixed one jack left another broken, and this didn't converge across several rounds of trying bigger and smaller values. What did fix it, in a single pass over the real, unmodified assembly: switching to a **perspective** projection (`focus` in `export_hlr`), with its apex centered on the model and a large focus distance so the visible distortion stays negligible. Perspective rays genuinely diverge from a point instead of running exactly parallel, which removes the coincidence orthographic has at every point in the frame, not just approximately at one tilt angle — and it happened to fix the 24-minute slowness too, down to under a minute. The apex must be centered on the model's own bounding box, not the STEP file's coordinate origin (this assembly's origin is nowhere near the part) — an off-center apex looks at the model from an angle no matter what direction you project, which showed up as the PCB's edge peeking out past one side of the panel but not the other.

The script doesn't use `cq.exporters.export` directly — it calls the same underlying HLR algorithm (`export_hlr` in the script) with an explicitly fixed screen-up vector. cadquery's own exporter lets OCCT auto-pick that reference axis, and it picks inconsistently: negating just the Y component of a working `projectionDir` silently mirrored the panel's silkscreen text backwards during testing. Fixing the axis explicitly makes every direction safe to use, including the three alternative isometric corners noted next to `VIEWS` in the script.

The output is then simplified (`SIMPLIFY_TOLERANCE`, 0.02 mm Ramer-Douglas-Peucker on each path) to cut file size 4-5x with no visible difference — the raw HLR curve discretization is far finer than any doc image needs — and cropped tightly to content (`PAD`, 2 mm margin) rather than sitting in a large padded canvas. Re-run after a mechanical change to the assembly STEP.
